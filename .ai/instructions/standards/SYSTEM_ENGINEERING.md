## 1. Манифест: за пределами вайбкодинга

Синтаксически корректный код — самый дешевый артефакт генеративного ИИ. «Вайбкодинг» (генерация по наитию без учета физических ограничений сред выполнения) порождает хрупкие системы, падающие под первой нагрузкой, теряющие деньги на гонках транзакций и зависающие из-за блокировки ввода-вывода.

Настоящая программная инженерия начинается там, где код встречается с суровой физической реальностью:
- с памятью, системными вызовами и блокировками I/O операционной системы;
- с конкурентными транзакциями, гонками данных и аномалиями СУБД;
- с сетевыми задержками, каскадными сбоями и отсутствием идемпотентности при повторах;
- с уязвимостями бизнес-логики (IDOR/BOLA), утечками секретов и атаками на цепочки поставок;
- с наблюдаемостью (Observability), когда инциденты расследуются по трейсам и метрикам, а не по `console.log`.

ИИ-ассистент **MUST NOT** выступать бездумным генератором кода. Модель **MUST** действовать как системный инженер, закладывая отказоустойчивость, корректные типы и инварианты данных на этапе проектирования.

## 2. Железо, ОС, память и асинхронный I/O

### 2.1 Неблокирующий I/O и защита Event Loop
В однопоточных асинхронных рантаймах (Node.js, Python `asyncio`, FastAPI) цикл событий обслуживает тысячи соединений.
- **MUST NOT** выполнять синхронные блокирующие системные вызовы в корутинах (`fs.readFileSync`, `time.sleep`, синхронный I/O сокетов).
- **MUST NOT** выполнять тяжелые CPU-вычисления в Event Loop: алгоритмы $O(N^2)$, ReDoS-уязвимые регулярные выражения, синхронный парсинг гигантских JSON-файлов (>10 МБ).
- **MUST** выносить CPU-интенсивные задачи в отдельные пулы воркеров (`Worker Threads`, `ProcessPoolExecutor`, фоновые очереди).
- **MUST** использовать потоковую (streaming) обработку данных (`Stream`, генераторы `chunk`) вместо вычитывания всего файла или ответа в оперативную память.

### 2.2 Дескрипторы файлов и системные вызовы
- Системный вызов (`syscall`) требует дорогостоящего переключения контекста `User Space -> Kernel Space -> User Space`. **MUST** использовать буферизованные операции ввода-вывода.
- **MUST** гарантировать закрытие файловых и сетевых дескрипторов при любых исходах, включая исключения (использовать `with` / `try...finally`), предотвращая ошибку ОС `EMFILE: too many open files`.

### 2.3 Память и сборка мусора (GC)
- Наличие Garbage Collector не защищает от утечек памяти.
- **MUST NOT** создавать глобальные коллекции, кэши или мапы без строгого лимита размера и политики устаревания (TTL, LRU-эвикция).
- **MUST** удалять слушатели событий (`removeEventListener`, `emitter.off`) при уничтожении компонентов.
- Контролировать Resident Set Size (RSS), избегать вытеснения страниц памяти в SWAP и предотвращать вмешательство Linux OOM Killer.

## 3. Данные, типы, сложность алгоритмов и транзакции

### 3.1 Алгоритмическая сложность и проблема N+1
- **MUST** анализировать вычислительную сложность алгоритмов. Запрещено использовать вложенные линейные проходы $O(N \times M)$ (`filter` внутри `some`/`find`), когда допустима индексация в `Set` / `Map` / `dict` за $O(1)$ со сложностью $O(N + M)$.
- **MUST NOT** допускать проблему N+1 запросов в ORM и репозиториях. Связанные сущности **MUST** подгружаться через Eager Loading (`JOIN`, `select_related`, `include`) либо пакетироваться через паттерн `DataLoader`.

### 3.2 Типобезопасность на границах и финансовые расчеты
- **Категорический запрет `float` / IEEE 754 для денег:** Двоичные числа с плавающей точкой порождают погрешности округления (`0.1 + 0.2 !== 0.3`). Расчет и хранение финансовых величин **MUST** выполняться строго в минимальных неделимых единицах (копейки, центы, сатоши в `int` / `BigInt`), либо в специализированных типах фиксированной точности (`Decimal` в Python, `NUMERIC`/`DECIMAL` в SQL).
- **Временные зоны:** Внутри доменной модели, в базах данных и API все метки времени **MUST** храниться и передаваться строго в формате **UTC ISO 8601** (`YYYY-MM-DDTHH:MM:SSZ`) или Unix Epoch Timestamp. Локализация часового пояса выполняется исключительно на клиенте в момент отображения в UI.
- **Валидация рантайма на границах:** Типизация TypeScript или Python Type Hints не существует во время выполнения. Любой ввод от пользователя или внешнего API **MUST** валидироваться строгими схемами (`Pydantic`, `Zod`, `TypeBox`) до передачи в бизнес-логику.

### 3.3 Индексы БД
- Таблицы без индексов при запросах с `WHERE` выполняют полное сканирование (`Seq Scan`).
- Выбирать тип индекса под сценарий:
  - **B-Tree:** дефолтный индекс для точечных поисков, диапазонов (`BETWEEN`, `>`, `<`) и сортировки (`ORDER BY`);
  - **Hash:** строгие равенства для длинных строк (хэши, точечные токены);
  - **GIN:** массивы, JSONB, полнотекстовый поиск.
- Помнить о стоимости индексов: каждый индекс замедляет операции `INSERT`, `UPDATE`, `DELETE`.

### 3.4 ACID и предотвращение Lost Update (Потерянных обновлений)
Наивный сценарий «прочитал баланс в память -> проверил -> записал новый» при параллельных запросах приводит к потере денег и отрицательным балансам.
Для защиты от гонок **MUST** применяться один из трех механизмов:
1. **Атомарные SQL-операции (предпочтительно):**
   ```sql
   UPDATE accounts SET balance = balance - 100 WHERE id = :id AND balance >= 100;
   ```
2. **Оптимистическая блокировка (Optimistic Locking):**
   Колонка `version` в строке:
   ```sql
   UPDATE accounts SET balance = balance - 100, version = version + 1 WHERE id = :id AND version = :old_version;
   ```
   Если затронуто 0 строк — повторить операцию с актуальной версией.
3. **Пессимистическая блокировка (Pessimistic Locking):**
   Использование `SELECT ... FOR UPDATE` внутри транзакции.

## 4. Сети и распределенные системы (Отказоустойчивость)

### 4.1 Заблуждения о распределенных вычислениях (Fallacies of Distributed Computing)
Сеть всегда ненадежна, задержка никогда не равна нулю, а пропускная способность конечна.

### 4.2 Паттерны устойчивости (Release It!)
- **Таймауты (Timeouts):** Любой сетевой вызов (HTTP, RPC, DB) **MUST** иметь явный тайм-аут на соединение (`connect_timeout`) и чтение (`read/socket_timeout`). «Голые» бесконечные запросы запрещены.
- **Exponential Backoff + Jitter:** При сбоях повторы **MUST NOT** сыпаться мгновенно. Задержка растет экспоненциально с добавлением случайного шума (Jitter):
  $$\text{sleep} = \min(\text{max\_delay}, \text{base} \times 2^{\text{attempt}}) + \text{random\_jitter}$$
  Это предотвращает эффект «громоподобного стада» (Thundering Herd) и лавинообразный отказ.
- **Автоматический выключатель (Circuit Breaker):** Изолирует сбойный сервис (`Closed -> Open -> Half-Open`), мгновенно возвращая ошибку (Fail-Fast) без перегрузки упавшей зависимости.

### 4.3 Идемпотентность и ключи идемпотентности (Idempotency Keys)
В распределенных сетях неизбежны дубли сообщений из-за сетевых таймаутов и повторов (семантика `At-least-once`).
- Операции изменения состояния (особенно финансовые и мутирующие `POST`) **MUST** поддерживать идемпотентность через `Idempotency-Key` (UUID операции).
- Защита от параллельных дублей: запись ключа в БД со статусом `IN_PROGRESS` до старта логики. Если параллельный повтор приходит до завершения — возвращать `409 Conflict` или ожидать завершения первого запроса.

### 4.4 Паттерн Transactional Outbox (Решение Dual-Write)
- **MUST NOT** делать прямую двойную запись вида `await db.order.create(); await kafka.send();`. Если отправка в брокер упадет, система рассинхронизируется.
- Событие **MUST** сохраняться в таблицу `outbox` в **той же локальной ACID-транзакции**, что и бизнес-сущность. Отдельный фоновый процесс вычитывает `outbox` и гарантированно доставляет сообщения в брокер с семантикой `at-least-once`.

## 5. Безопасность, авторизация и цепочки поставок

### 5.1 Авторизация на уровне объектов (BOLA / IDOR)
- Проверка факта аутентификации пользователя недостаточна.
- Любой доступ к сущности по идентификатору **MUST** сопровождаться проверкой прав владения:
  ```sql
  SELECT * FROM orders WHERE id = :order_id AND user_id = :current_user_id;
  ```

### 5.2 Инъекции (SQL, Command Injection)
- **MUST NOT** конкатенировать пользовательские строки в SQL-запросы или команды ОС (`exec(cmd + input)`).
- **MUST** использовать только параметризованные запросы (`Prepared Statements`) и безопасные вызовы процессов с передачей аргументов списком без shell-интерпретации.

### 5.3 Хранение паролей и токенов
- Алгоритмы SHA-256 и MD5 **ЗАПРЕЩЕНЫ** для паролей (они уязвимы для перебора на GPU). Пароли хешируются строго через `Argon2id` или `bcrypt`.
- Чувствительные токены авторизации **MUST NOT** храниться в незащищенном `localStorage` браузера (риск кражи через XSS). Сессионные куки передаются с флагами `HttpOnly`, `Secure` и `SameSite=Strict/Lax`.

### 5.4 Защита от атак на зависимости (Slopsquatting и галлюцинации LLM)
- ИИ склонен галлюцинировать имена пакетов. Злоумышленники регистрируют такие имена в npm и PyPI с вредоносным кодом.
- **MUST** строго фиксировать хэши и версии зависимостей через lock-файлы (`package-lock.json`, `poetry.lock`, `requirements.txt` с хэшами).
- Перед предложением стороннего пакета **MUST** убедиться в его реальном существовании и репутации.

## 6. Архитектура, тестирование и наблюдаемость (Observability)

### 6.1 Слабая связность и инверсия зависимостей (Low Coupling & Dependency Inversion)
- Бизнес-логика ядра **MUST NOT** зависеть от деталей реализации: конкретной СУБД, облачного SDK или фреймворка UI.
- Взаимодействие строится через абстрактные интерфейсы/протоколы (Dependency Injection).

### 6.2 Пирамида тестирования и Property-Based Testing
- Unit-тесты проверяют чистые функции и инварианты без сетевых задержек.
- Интеграционные тесты проверяют реальные контракты БД и брокеров (с использованием изолированных окружений).
- **Property-Based Testing (Hypothesis, Fast-Check):** Тестирование не на 2–3 придуманных примерах, а на тысячах псевдослучайных граничных значений (пустые строки, отрицательные числа, Unicode, спецсимволы, `MAX_INT`) для математического доказательства инвариантов.

### 6.3 Наблюдаемость по стандартам SRE
- **Структурированное логирование:** Запрещен неструктурированный вывод через `print()` / сырой `console.log`. Логи пишутся в JSON с едиными полями: `timestamp`, `level`, `service_name`, `trace_id`, `user_id`, `error_stack`.
- **Перцентили вместо среднего (Percentiles over Mean):** Среднее арифметическое скрывает проблемы (Tail Latency). Анализ задержек ведется по перцентилям `p50`, `p95`, `p99`.
- **Метрики RED:** Rate (RPS), Errors (процент ошибок), Duration (длительность обработки по перцентилям).
- **Распределенная трассировка:** Сквозная передача `TraceID` (стандарт W3C TraceContext) через все вызовы микросервисов, баз данных и очередей.

## 7. Инженерная матрица самоконтроля AI-ассистента

Перед тем как предложить или сгенерировать код, проверьте реализацию по матрице:

| Область | Опасный вайбкодинг (ЗАПРЕЩЕНО) | Системная инженерия (ОБЯЗАТЕЛЬНО) |
|---|---|---|
| **Вычисления и I/O** | Синхронный блокирующий I/O, тяжелые вычисления в Event Loop, незакрытые дескрипторы | Неблокирующий I/O, worker threads для тяжелых задач, гарантированное закрытие ресурсов (`with`) |
| **Сложность алгоритмов** | Вложенные методы массивов $O(N^2)$, N+1 запросов в цикле | $O(1)$ Hash Map/Set lookup, Eager Loading (`JOIN`) и DataLoader |
| **Типы и величины** | `float` для денег, смешение временных зон, отсутствие валидации рантайма | Минимальные неделимые единицы (`int`/`BigInt`) или `Decimal`, строгий UTC ISO 8601, схемы Pydantic/Zod |
| **Базы данных** | Наивный `read-modify-write` (Lost Update), отсутствие индексов под `WHERE` | Атомарный SQL-апдейт, оптимистичные/пессимистичные блокировки, профилирование индексов (B-Tree/GIN) |
| **Сетевые вызовы** | «Голый» запрос без таймаутов, моментальный ретрай (DDoS) | Жесткие таймауты (connect/read), Exponential Backoff + Jitter, Circuit Breaker, Idempotency-Key |
| **Распределенность** | Двойная запись подряд в БД и брокер (Dual-Write) | Паттерн Transactional Outbox внутри единой ACID-транзакции |
| **Безопасность** | Прямая выборка по ID без проверки владельца (IDOR), конкатенация строк в SQL | Проверка владения объектом (`user_id`), параметризованные запросы, Argon2id/bcrypt для паролей |
| **Зависимости** | Использование непроверенных/галлюцинированных библиотек | Проверенные пакеты, фиксация хэшей в lock-файлах |
| **Архитектура** | Смешение SQL, бизнес-логики и UI в одном монолите | Dependency Inversion, чистые границы слоев, фиксация решений в ADR |
| **Наблюдаемость** | Хаотичные `print()` / `console.log`, среднее арифметическое задержки | Структурированный JSON-лог (`trace_id`), метрики RED, перцентили p95/p99, OpenTelemetry |
